# 九个 skill 的定义质量审阅（针对 v1.1.7）

> 审阅对象：`skills/*/SKILL.md` 9 份、`references/` 下 21 份文件（其中 20 份为规范库母本的同名副本，1 份是 `unit-writer` 独有的 `写作范式.md`）、`scripts/` 下 7 个脚本、`assets/` 下 8 份模板
> 审阅方式：机器可查项全部实跑（引用路径存在性、副本哈希、步骤编号、术语分布、description 长度与边界词），其余逐文件通读
> 审阅日期：2026-10-24

---

## 结论先说

**结构组织是这套东西最强的地方，不用大改。** 九份 `SKILL.md` 全部是同一个六节骨架（适用场景 / 输入要求 / 执行步骤 / 输出格式 / 质量要求 / 禁止事项），步骤编号 5–10 步全部连续无跳号，description 引号风格完全统一（全用英文双引号），7 个脚本的副本组 md5 一致。这种一致性在同类仓库里不常见。

**真正要修的是「同步」和「边界」两件事**，共 12 项，其中 3 项 P0——它们不是文风问题，是会导致错误行为的问题。

最严重的一条：**`规范库/审校标准.md` 是 v1.0，而 `skills/textbook-reviewer/references/审校标准.md` 是 v1.1。母本比副本旧。** 按 README 里那条同步命令执行一次，会把 v1.1 新增的「只能人工判的项」整节覆盖掉。

## 优先级定义

| 级别 | 判据 | 数量 |
|---|---|---|
| **P0** | 会直接导致错误行为、规则丢失或命令跑不通 | 3 |
| **P1** | 会造成判定不一致、返工，或让规则「存在但没人用」 | 6 |
| **P2** | 影响可读性与长期维护成本，不影响当前正确性 | 3 |

## P0

### P0-1 审校标准母本比副本旧，同步命令会回退规则

**位置**：`规范库/审校标准.md`（v1.0，60 行）vs `skills/textbook-reviewer/references/审校标准.md`（v1.1，86 行）

**证据**：两份文件差异 148 行。副本多出整节 `## 五、只能人工判的项（脚本不覆盖，须写进报告第 5 节）`，母本没有。

**为什么严重**：README 第九节写着同步命令 `cp 规范库/*.md skills/textbook-reviewer/references/`。任何一次"照文档同步"，都会用 v1.0 覆盖掉 v1.1，**静默丢失新增的人工判项清单**。而且 reviewer 的 `SKILL.md` 步骤 2 明确要求"逐条过 `references/审校标准.md` 的 SJ-X1 ~ SJ-X5"，它读到的是哪一版，取决于上一次谁同步过。

同时发现副本自身有个编号错误：

```
## 五、审校的边界
## 五、只能人工判的项（脚本不覆盖，须写进报告第 5 节）
```

两个「五」，没有「六」。v1.1 加节时把编号顶掉了。

**建议**：

1. 以副本为基准，把「只能人工判的项」搬回母本，母本升 v1.1（这是唯一正确的方向——副本内容是有效的）。
2. 母本里把第二个「五」改成「六、只能人工判的项」，并把正文里的「报告第 5 节」改成「报告第六节」（`审校标准.md` 内部的自引用要跟着改）。
3. 再 `cp` 回副本，让两边一致。
4. **加一条硬规矩**：`规范库/` 只能向前改，副本永远由母本单向生成。现在的做法是双向手工同步，两个方向都走过，所以出现了"副本更新"这种结构性问题。

**顺带**：`审校标准.md` 母本状态行写「v1.0 待学科专家审定」，而 README 与 CHANGELOG 都说规则库已到 v1.4/v1.5。这份文件的版本号体系与其他四份脱节，建议统一。

### P0-2 九份 description 里八份没有边界声明

**位置**：`skills/*/SKILL.md` 的 `description` 字段

**证据**：

| skill | description 字符数 | 含「不适用 / 不负责 / 不要」 |
|---|---|---|
| curriculum-mapper | 195 | 无 |
| exercise-designer | 175 | 无 |
| material-creator | 168 | 无 |
| outline-designer | 228 | 无 |
| textbook-analyzer | 185 | 无 |
| textbook-builder | 181 | 无 |
| textbook-formatter | 195 | **有**（"不负责封面设计、开本、色彩与印刷工艺"） |
| textbook-reviewer | 211 | 无 |
| unit-writer | 236 | 无 |

**为什么严重**：Agent Skills 是**渐进加载**——第一层只读 `name` + `description`，正文的「适用场景 / 不适用」要等技能被选中后才加载。也就是说：**在决定"该不该用这个 skill"的那一刻，模型看不到边界信息。**

九份文件正文里都写了「不适用：……（→ 某某 skill）」，写得还很好，但这句话对路由环节是无效的。后果是典型的误触发：用户说"帮我把这一课排成 Word"，`unit-writer` 的 description 里有"撰写…正文"，可能先被选中，写完才发现在该排版。

**建议**：把正文的「不适用」一行直接搬进 description 末尾，格式统一为：

```
……用户说"X""Y"时同样使用。不用于：设计大纲（→ outline-designer）、
出习题（→ exercise-designer）、审校（→ textbook-reviewer）。
```

九个文件各加 20–40 字，仍远低于 description 的常见上限。这条改动成本最低、收益最高，**建议第一个做**。

**附带**：`unit-writer` 的 description 结构可以顺手理顺。现在是：

> 「当用户已有大纲中的某一课，要求"写一课""写这一节"……时使用。输入为大纲文件 + 节标识……；输出为……，可直接交给 textbook-reviewer 审校。」

中间插了输入输出说明，随后又接一句「或要把一课改写成另一学段版本、只写导语与案例、照着范文写一课、需要一课 3000 字的正文时使用」——触发语被切成两段，第二段接在输入输出之后，读起来断裂。建议把全部触发语归到一句里，输入输出放后面。

### P0-3 脚本调用路径依赖当前目录，装完大概率跑不通

**位置**：七个 skill 的「执行步骤」

**证据**（原文摘录）：

```
curriculum-mapper : python scripts/check_lo.py <LO表.csv>
exercise-designer : python scripts/check_exercise.py <习题.md>
outline-designer  : python scripts/check_outline.py <大纲文件>
textbook-analyzer : python scripts/render_pages.py <教材.pdf> --probe
textbook-reviewer : python scripts/check_draft.py <稿件.md> --json
unit-writer       : python scripts/check_draft.py <稿件.md>
textbook-formatter: python ../unit-writer/scripts/check_draft.py <稿件.md>
```

**为什么严重**：`scripts/...` 是相对于**当前工作目录**的。skill 被安装到 `~/.claude/skills/unit-writer/` 后，用户的工作目录是他的教材项目（比如 `~/work/信息管理教材/`），那里没有 `scripts/` 子目录——**命令直接报 `No such file or directory`**。

更矛盾的是：README 第三节的「验证装对了」写的是全路径 `$SKILLS/unit-writer/scripts/check_draft.py`，说明作者清楚要用全路径，但 `SKILL.md` 里没跟着改。

`textbook-formatter` 的 `../unit-writer/scripts/` 更脆弱：它假设两个 skill 是相邻目录。用户只装了 formatter 一个 skill，或装了改名版本，就断了。

**建议**：全部改成显式占位符 + 一句前置说明：

```markdown
本 skill 内的命令一律以 skill 目录为基准，`<SKILL_DIR>` 指本 skill 所在目录：

python <SKILL_DIR>/scripts/check_draft.py <稿件.md>
```

并在文档页首统一加一行（九份各一份）：

> 命令中的 `<SKILL_DIR>` 替换为本 skill 的实际路径，例如 `~/.claude/skills/unit-writer`。

`textbook-formatter` 那条改为调用自己目录的副本更稳（它没有 `check_draft.py` 副本，可以补一份，成本是一个 `cp`）。

## P1

### P1-1 `unit-writer` 仍写着「用『然而』」，规则早已改为「反转出问题」

**位置**：`skills/unit-writer/SKILL.md` 步骤 3

**原文**：

> ② 用「然而」把好处翻成麻烦；

**母本现状**（`规范库/体例规范.md` TY-06）：

> ② **反转出问题**——把好处翻成麻烦；

**为什么要修**：这正是本项目在 v1.1.4 修正过一次的错误——当时把"范文用了『然而』"写成了"必须用『然而』"，后来发现范文其实用的是立场对立，规则改成了「反转出问题」+ 三种合法形态。`规范库/` 改了，`SKILL.md` 没跟。

这条比一般的不同步更值得说，因为它会把作者**引回已经被推翻的写法**，而且看上去像规则，不像笔误。

**建议**：改为与 TY-06 一致的表述，并把三种合法形态指过去：

> ② **反转出问题**——把好处翻成麻烦。可用「然而」承接，也可用立场对立或场景反差，三种形态见 `references/体例规范.md` TY-06；

### P1-2 `语言风格.md` 有三份副本，没有任何 SKILL.md 提到它

**位置**：`skills/unit-writer`、`material-creator`、`textbook-reviewer` 的 `references/` 各有一份 `语言风格.md`

`unit-writer` 步骤 2 只说了读 `体例规范.md`（六栏定义）和 `写作范式.md`，漏掉了语言风格这一份。

- `unit-writer` 步骤 2 补一句：「再读 `references/语言风格.md`，禁用词表与句长段长限制以此为准。」
- `textbook-reviewer` 步骤 3（五维评分里的"语言规范"维度）补引用。
- `material-creator` 步骤 5 写案例时补引用（案例正文同样受限）。

**位置**：`skills/unit-writer/SKILL.md` 步骤 4 前置校验

**位置**：`skills/unit-writer/scripts/check_draft.py` 第 21–23 行

```python
"本科高年级": {"导语": (150, 250), "正文": (3000, 4500), "案例": (800, 1200), "拓展": (100, 200),
               "练习比例": (5, 3, 2), "段限": 200},

```

**当前状态**：与 `规范库/学段适配.md`、`体例规范.md` TY-11 **完全一致**——所以现在不是 bug。

**为什么要管**：这是"规则 → 副本 → 脚本"三段链里的第三段。改 `学段适配.md` 的区间，前两段有同步命令管，脚本这一段没人管，也不会有任何报错。**判定与规则悄悄分叉**，而且分叉后脚本更"权威"（它会报 ERROR）。

**建议**（按成本从低到高，任选其一）：

1. 脚本顶部加一行注释：`# 本表须与 规范库/学段适配.md 同步；改动时同步 test 用例`（成本最低，靠人）。
2. 加一个 `tools/consistency_check.py`，解析 md 表格里的区间与脚本字典比对，不一致就报错（推荐，见 P1-6）。
3. 让脚本直接从 `学段适配.md` 解析区间（最彻底，但会让脚本依赖 md 格式，脆弱）。

### P1-6 缺一个自动一致性检查，这次的问题全靠人工发现

**观察**：本次审阅找到的 12 项问题里，有 5 项属于"两个文件该一致却不一致"：母本 vs 副本、SKILL.md vs TY-06、SKILL.md 引用 vs 实际文件、脚本参数 vs 母本、命名规则 vs README。

这些**全部可以机器判**，却全部靠人工翻文件发现。而且 `tools/trigger_test.py` 只测触发，不测一致性。

**建议**：新增 `tools/consistency_check.py`，检查五件事，任一不过就非零退出：

```python
1. 每个 skill 的 references/*.md 与 规范库/同名文件 md5 一致
2. SKILL.md 里 `references/`、`assets/`、`scripts/` 的引用路径全部存在
3. SKILL.md 里出现的学段数值（正则捞 (150, 250) 这类）与 学段适配.md 一致
4. 九个 SKILL.md 的二级标题集合相同（允许 outline-designer 多一节且该节被标注为例外）
5. 步骤编号连续（1..n 无跳号）
```

这个脚本大约 120 行，写一次能挡住后面所有同类问题。**这是本次审阅里投入产出比最高的建议**，优先级可以按 P1 处理。

## P2

### P2-1 「单元 / 课」与「章 / 节」两套术语没有对照

**证据**（各 `SKILL.md` 中术语出现次数）：

| skill | 章 | 单元 | 课 |
|---|---|---|---|
| outline-designer | 7 | 42 | 51 |
| formatter | **16** | 1 | 9 |
| unit-writer | 1 | 6 | 27 |
| textbook-analyzer | 5 | 0 | 0 |

`outline-designer` 输出的是「## 单元 N」，`unit-writer` 写「第 N 单元第 M 课」，到 `formatter` 突然全变成「章首页」「本章提要」「章末参考文献」——**排版环节把「单元」叫成「章」，但没有任何一处说明这两个词是同一个东西**。

**建议**：在 `体例规范.md` 开头或 `formatter/SKILL.md` 输入要求里加一句对照：

> 本系列的「单元」对应出版形态的「章」，「课」对应「节」。排版环节一律用「章/节」，写作环节用「单元/课」，两者指同一层级。

### P2-2 产物命名在 SKILL.md 与 README 之间不一致，且有一处缺失

| 环节 | SKILL.md 里 | README 里 |
|---|---|---|
| 正文 | `<course-slug>-u<单元号>-l<课号>.md` | `<slug>-u<单元>-l<课>.md` |
| 审校报告 | `<course-slug>-review-u<单元>-l<课>.md` | `<slug>-review-u_-l_.md` |
| 习题 | **未规定** | `<slug>-ex-u<单元>-l<课>.md` |

`exercise-designer` 的「输出格式」只给了内容骨架，步骤 8 说"按模板输出"，**没有规定文件名**——下游 `unit-writer` 的练习栏、`formatter` 的汇总都可能找不到它。

**建议**：统一用 `<course-slug>-…` 前缀（更明确），README 表同步；`exercise-designer` 补一条命名规则。

**位置**：`skills/outline-designer/SKILL.md` 末节「学段默认参数」

## 建议的修复顺序

| 顺序 | 做什么 | 为什么排这个位置 | 预估改动量 |

| 1 | **P0-1** 审校标准母本 ← 副本 v1.1，修两个「五」 | 不先修，后面任何同步动作都可能丢规则 | 改 1 个文件，搬 1 节，改 1 处编号引用 |

| 3 | **P0-3** 脚本路径统一为 `<SKILL_DIR>/scripts/…` | 不修的话，用户装完第一条命令就失败 | 9 处命令 + 9 行说明 |
| 4 | **P1-6** 写 `tools/consistency_check.py` | 前三条修完立刻用它守门，防止复发 | 新增 1 个脚本（约 120 行） |
| 5 | **P1-1 / P1-2 / P1-3 / P1-4** 四处局部修正 | 都是单点文本改动，可一次提交 | 4 处句子 |
| 6 | **P1-5 / P2-1 / P2-2 / P2-3** 收尾 | 前五项做完后，这几条可以用新脚本自动查出 | 4 处 |

做完 1–4 项后跑一次 `consistency_check.py`，应当只剩 P2 的三项；这三项可以用脚本兜住，不必急着改。

## 一句话总结

这套 skill 的**写法质量高于它的维护机制**：每份 `SKILL.md` 单看都很扎实（有边界、有缺失处理、有可判定的禁令），但九份之间的关系靠人记——谁是母本、哪份副本更新、命名该长什么样，全靠自觉。P0-1 那条就是自觉失效的产物：副本被改新了，母本没跟上，而文档里的同步命令指向的是反方向。

修完 P0 三条 + 补一个一致性脚本，这套东西就从"写得好的九份文件"变成"有护栏的一套资产"。
