# 教材编写项目总控（textbook-builder）

## 适用场景

- 用户刚开一个新教材项目，不确定从哪一步开始。
- 项目做到一半，用户问"下一步做什么"。
- 多节课并行时，需要知道哪些产物齐了、哪些还缺。
- 用户同时提出跨环节的要求（如"先看看结构，再写两课"），需要拆成有序的步骤。

不适用：任何具体的写作与审校动作（交子 skill 做）；只写一课（直接 `unit-writer`）。

## 输入要求

| 输入 | 说明 | 缺失处理 |
|---|---|---|
| 项目目录 | 含 `项目状态.md` 与产物文件的目录 | 没有状态文件时，按 `assets/项目状态模板.md` 现建一份，并向用户确认课程名、学段、总学时 |
| 用户的当前请求 | 一句话意图 | 必给 |

**项目状态文件**是唯一可信来源。不要在对话里凭记忆判断进度。

## 执行步骤

1. **读状态**。读 `项目状态.md`，取出：课程名、学段、总学时、各产物完成情况、上次停在哪一步。
2. **判定环节**。按下面的判定表定位当前环节。判定依据是**产物是否存在且通过自检**，不是用户说"我写完了"。
3. **查前置**。若目标环节的前置产物缺失或不合法，先补前置，不要跳步。

| 当前环节 | 前置条件（缺则回退到它） | 该调用的 skill |
|---|---|---|
| 0 需求定义 | 无 | 人工，输出 `需求说明书.md` |
| 1 样本拆解 | 有 3–5 套样本 | `textbook-analyzer` |
| 2 课标映射 | 有课标/培养方案 | `curriculum-mapper` |
| 3 大纲设计 | 有 LO 表或等价目标清单 | `outline-designer` |
| 4 正文撰写 | 大纲通过 `check_outline.py` | `unit-writer` |
| 5 练习设计 | 有该课稿件 | `exercise-designer` |
| 6 素材编写 | 有案例方向 | `material-creator` |
| 7 审校 | 六栏齐全的稿件 | `textbook-reviewer` |
| 8 排版输出 | 审校结论为通过 | `textbook-formatter` |

4. **给一次性回复**。回复必须包含三件事：当前在第几步、这一步要什么输入、下一步做什么。不超过 5 行，不要复述整份状态文件。
5. **更新状态**。每完成一个环节，追加一行到 `项目状态.md` 的「进度流水」，写明日期、产物文件名、自检结论。

## 输出格式

**路由结论（对话内，5 行以内）**：

```
当前：第 3 步 大纲设计（已完成 6 单元，第 5、6 单元缺篇幅配额）
缺：第 5、6 单元每课的 `- 篇幅：` 行
下一步：补篇幅后跑 check_outline.py，通过即可进第 4 步写正文
```

**状态文件**：按 `assets/项目状态模板.md` 维护，含「基本信息 / 产物清单 / 进度流水 / 待决事项」四块。

## 质量要求

- 判定必须基于文件事实：产物存在、能通过对应脚本、文件名符合命名规则，三者齐才算完成。
- 一次只推进一个环节。用户要求"顺便把正文也写了"时，先确认大纲合法，再交 `unit-writer`。
- 状态文件与对话结论不一致时，以文件为准，并当场更正状态文件。
- 每个环节交接时写清"交接物是什么文件"，禁止用"上面那段大纲"这类指代。

## 禁止事项

- 不得越权代写正文、练习、审校报告。
- 不得因为用户催促而跳过自检脚本。
- 不得在状态文件里写"基本完成""大致可以"这类无法核对的描述。
- 不得自行发明新环节（第 9、10 步）；流程固定为 0–8 共九步。
